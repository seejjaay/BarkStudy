# M6b: releases on GitHub (release-please, release.yml, signing hook, winget, repo docs)

## Context

M6a made a verified installer and an updater that work locally. M6b turns a merge into a public release that existing installs update to. M6 acceptance: pushing a release produces an installer on GitHub Releases, existing installs auto-update to it, and `winget install` works. Signing and winget can't be finished inside this milestone, because both wait on things only CJ can do.

What CJ decided (2026-11-03):

- `main` was pushed directly. Main and M6b work from here on go through a branch and a PR, so the new workflows run in CI before they land.
- SignPath isn't applied for yet.
  - CJ applies now.
  - Until approval, releases are **unsigned betas**, and the release notes say SmartScreen will warn.
  - The signing step is written, but it's skipped until the SignPath secrets exist.
  - 1.0 waits for signing.
- Versions come from **release-please**, which turns conventional commits into a release PR.
- **winget** is wired, but runs only for stable releases at or above 1.0, and only once a `WINGET_TOKEN` secret exists.

One more decision this plan makes (override it if wrong): **0.x releases are normal GitHub releases, not prereleases.**

- electron-updater only offers prereleases to people with "Include beta versions" on.
- If every 0.x were a prerelease, a tester who left beta off would never be updated.
- `-beta.N` tags stay reserved for the beta channel later (M7).
- winget is held back by the ≥ 1.0 gate, not by the prerelease flag.

Every task ends with `npm run typecheck && npm run lint && npm test` green. Each commit is CJ-confirmed.

## Tasks

### T1. release-please

- `release-please-config.json`:
  - Release type `node`, one package at `.`, with `include-v-in-tag`.
  - Changelog sections: feat, fix, perf and docs shown; chore, test, refactor and ci hidden.
  - `bump-minor-pre-major: true`, so a `feat!` doesn't jump 0.x to 1.0 by accident.
- `.release-please-manifest.json` holds `{ ".": "0.1.0" }` (the current version). The first release PR covers everything since then.
- `.github/workflows/release.yml`, job `release-please`:
  - Runs `googleapis/release-please-action`, pinned to a commit SHA, on push to `main`.
  - Permissions: `contents: write`, `pull-requests: write`, and nothing else.
  - Outputs `release_created` and `tag_name`.
- **CI doesn't run on the release PR.** That PR is opened with `GITHUB_TOKEN`, and GitHub doesn't start workflows from it. The PR only changes `package.json` and `CHANGELOG.md`, so this is accepted rather than adding a personal access token. Note it in `docs/release.md`.

### T2. Build and publish job (same workflow)

- Job `publish`:
  - `needs: release-please`, `if: release_created`, `runs-on: windows-latest`.
  - Permissions: `contents: write` only.
- Steps:
  1. Checkout at the tag, `npm ci`, `npm run typecheck`, `npm run lint`, `npm test`.
  2. `npm run package`, then `node scripts/verify-package.cjs`, which has to pass before anything is uploaded.
  3. Signing (T3). It's skipped while the secrets are missing.
  4. `gh release upload <tag>` with `BarkStudy-Setup-X.exe`, `.blockmap` and `latest.yml`.
     - The `gh` CLI does the upload, not electron-builder's publisher, so there's one upload mechanism and no draft juggling.
     - The `publish:` block in `electron-builder.yml` stays, only to write `app-update.yml`.
  5. If the build is unsigned, prepend a release-notes banner with `gh release edit`: **"Unsigned beta: Windows SmartScreen will warn. Choose More info → Run anyway."**
- **The gap is accepted.** The release exists a few minutes before its assets. An updater check in that window finds no `latest.yml`, fails quietly, and retries next cycle.
- **Pinning:** every third-party action is pinned to a full commit SHA, with the version in a comment. That guards the supply chain (someone else's compromised action running with our token). Dependabot already bumps actions weekly.

### T3. Signing hook (SignPath, off until approved)

- The step only runs when `SIGNPATH_API_TOKEN` and the org and project ids exist (`if: env.SIGNPATH_API_TOKEN != ''`).
- When on, the order matters, because electron-builder writes the installer's hash into `latest.yml`:
  1. Sign `win-unpacked/BarkStudy.exe` through SignPath.
  2. Build the installer from the signed folder (`electron-builder --prepackaged release/win-unpacked`).
  3. Sign the installer.
  4. Recompute `latest.yml`'s `sha512` and `size` for the signed installer with `scripts/update-latest-yml.cjs`, and drop the blockmap, so updates fall back to a full download.
- Before the upload, a check confirms that `latest.yml` matches the installer's actual hash. The updater rejects a mismatched file, which is the real risk here.
- `scripts/update-latest-yml.cjs` is unit-tested in `tests/main/latestYml.test.ts`, on a fixture `latest.yml` and a fake installer.
- The SignPath leg itself can't be tested until approval. The PR says so, and `docs/release.md` gets a "first signed release" checklist.

### T4. winget (off until 1.0 and a token)

- A `winget` job, `needs: publish`, runs only when all of these hold:
  - the tag is not a prerelease
  - the major version is ≥ 1
  - `secrets.WINGET_TOKEN != ''`
- It runs `wingetcreate update seejjaay.BarkStudy --version X --urls <installer url> --submit --token`.
- `wingetcreate update` needs the package to exist already, so the first submission is manual (`wingetcreate new`), done once by CJ at 1.0. `docs/release.md` gets the steps and the package id `seejjaay.BarkStudy`.

### T5. Repo docs

- **`README.md`:** keep the safety section and the development section, and add:
  - what it is, with one screenshot placeholder named as a todo
  - install, including the SmartScreen note while unsigned
  - how updates work
  - privacy in three lines, linking `PRIVACY.md`
- **`PRIVACY.md`:**
  - **What's read:** window positions and z-order, the foreground app's process name, idle time, battery saver. Never window titles, window contents or screenshots.
  - **What's stored:** the userData files, listed.
  - **The one network call:** the update check against this repo's GitHub Releases, and how to turn it off.
  - No telemetry, and crash dumps stay local.
  - Facts come from the Global Constraints and the code. Each claim is checked against `src/` before writing.
- **`SECURITY.md`:** report through GitHub's private vulnerability reporting, which CJ turns on in the repo settings. It also covers what counts as in scope.
- **`CONTRIBUTING.md`:** setup (`npm ci`, `node node_modules/electron/install.js` under npm 12), the check commands, conventional commits, and the invariant and replay tools.
- **Templates:**
  - `.github/ISSUE_TEMPLATE/bug_report.yml` asks for About → **Copy diagnostics**, plus steps to reproduce.
  - `feature_request.yml`.
  - `config.yml` turns off blank issues and links security reports to `SECURITY.md`.
  - `.github/pull_request_template.md`.
- **Links:** add `privacy` to `LINKS` ([links.ts](../../../src/main/links.ts)) and a "Privacy" link on About, so the allowlist matches the Global Constraints. `links.test.ts` already checks every link stays on the repo.

### T6. First real release (the GitHub leg of S5)

2. CJ merges that release PR.
3. Expect: tag `v0.2.0`, a release with the installer, blockmap and `latest.yml`, and the unsigned banner.
4. Update test against GitHub:
   - Install `v0.2.0` from the release page, which also covers test-matrix rows 32 and 36 by hand.
   - Land any `fix:` commit, so release-please cuts `v0.2.1`.
   - The installed 0.2.0 should find, download and restart into 0.2.1.
5. Record the result in `docs/spike-results.md` (the GitHub leg of S5) and in `docs/test-matrix.md`.
